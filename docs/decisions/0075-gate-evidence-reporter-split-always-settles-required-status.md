# 0075. A non-cancelling reporter job owns the required gate-evidence status, always settling the final head

## Status

Accepted — 2026-09-20 ([issue 2262](https://github.com/mfittko/dev-loops/issues/2262))

## Context

Amends [0043](./0043-gate-evidence-verdict-comment-refire.md), which coalesces `gate-evidence` runs per PR through a job-level `concurrency: cancel-in-progress: true` group and bars a superseded run from posting via `!cancelled()`. That design accepted two residuals (a facts-step API failure, and a draft-PR comment cancelling a live run) but missed a third: a rapid burst of review/comment events at a clean PR close — the gate's own thread-reconciliation plus a head-pinned `approve merge` comment — cancels each in-flight run as the next one starts. When the LAST-triggered run of the burst is itself cancelled (superseded, or cancelled during shutdown), no run in the burst ever reaches the status-posting step, so the required `gate-evidence` check is left pending/stale/cancelled at the final head even though the evidence is genuinely satisfied. Observed merging PR 2247: `mergeStateStatus: BLOCKED`, ten `gate-evidence-runner: CANCELLED` check runs, every substantive check green, and `gh pr merge` reporting only GitHub's generic "the base branch policy prohibits the merge" — no indication of the real cause.

## Decision

Split the one job into two. `gate-evidence-runner` keeps job-level `cancel-in-progress: true` (its waste-avoidance on rapid re-triggers is worth keeping) and the compute-heavy work (checkout, install, `detect-checkpoint-evidence.mjs`), but no longer posts a status — it only exposes its verdict as a job output (`evidence_state`). `gate-evidence-reporter` (`needs: [gate-evidence-runner]`, `if: always() && needs.gate-evidence-runner.result != 'skipped'`) owns the required `gate-evidence` status and runs in its OWN non-cancelling group (`cancel-in-progress: false`). A reporter run still queued when a newer one is queued is superseded and dropped without executing (it would only post a state the newer event already supersedes); a reporter run already RUNNING is never killed. The run triggered by the final event in a burst is therefore always the one that gets to execute and post, closing the gap regardless of how many detector runs in the burst were cancelled — including the last-triggered one. The reporter resolves number/draft/head SHA independently (a verbatim copy of the detector's Resolve-PR-facts step, so it does not depend on the detector's outputs having been written) and reuses the detector's `evidence_state` when present; when it is empty (the detector was cancelled or failed before writing it), the reporter recomputes independently via the same trusted default-branch checkout and detector invocation. The definitive-only status contract (#1702: `satisfied` → `success`, everything else → `failure`, never `pending`) and the trusted-base evaluation provenance (0034/0043: default-branch checkout, `persist-credentials: false`) are both preserved unchanged in both jobs. Separately, `merge-pr.mjs` now inspects the `gate-evidence` context on a merge blocked by `gh pr merge` (branch-protection block after every wrapper precondition — including CI-green, which already excludes `gate-evidence` — passed) and, when that context is not `success`, appends the real cause and the transitional recovery (complete/re-run the latest Gate-evidence run, or edit the current-head verdict comment) to GitHub's generic stderr rather than leaving the operator with only "the base branch policy prohibits the merge."

## Consequences

A burst of review/comment events at a clean close can no longer leave a satisfied PR's required check stuck: the reporter's non-cancelling group guarantees a completed, status-posting run at the final head, whether or not any detector run in that burst survived. The `!cancelled()` no-spurious-failure guarantee is trivially preserved because the detector no longer posts at all. One accepted residual: the reporter's `if: always()` depends on GitHub running a `needs` job whose dependency was CANCELLED by that dependency's own JOB-level concurrency group — the workflow RUN itself is not cancelled, only the one job, so `needs.<job>.result` reports `cancelled` (not `skipped`) and `always()` still starts the reporter; this is documented GitHub Actions behavior, not new fail-open surface. A second accepted cost: every reporter run now spends one extra job's worth of scheduling overhead (though only the reporter's own draft/decide steps, not necessarily the full checkout/install/detect chain, since that only runs on the recompute path), in exchange for guaranteed settlement. `scripts/github/reconcile-gate-evidence-status.mjs` (0057) is unaffected: it targets a run id parsed from the status `target_url`, and detector and reporter jobs sharing one workflow run means re-running that id still re-executes both.
