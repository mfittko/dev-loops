# 0075. Findings below a per-gate inline severity floor fold into the verdict body instead of posting inline threads

## Status

Accepted — 2026-09-20 ([PR 2295](https://github.com/mfittko/dev-loops/pull/2295))

## Context

Every locatable gate finding, `low` and `nit` included, posted as its own resolvable inline PR review thread ([0046](./0046-one-review-surface-per-gate-round.md) governs the single verdict surface; the inline finding comments hang off it). A human reviewer then had to open, read, and dispose of a thread per finding — including the ones the review itself already judged low value. Consumer-repo feedback named this as noise: the `low`/`nit` disposition and the net-reduction filing decision both ran off thread resolution (`close-gate-findings.mjs`), and `unresolvedGateThreadCount` blocked ready-for-review while any gate-authored thread dangled ([1585](https://github.com/mfittko/dev-loops/issues/1585)). GitHub's own suppressed-comments UX is Copilot-only and not API-writable, so it cannot be reused. [Issue 2263](https://github.com/mfittko/dev-loops/issues/2263) ordered the low-value findings folded off the inline surface by default.

## Decision

A new per-gate `gates.<gate>.inlineSeverityFloor` (default `"medium"`) sets the lowest severity still posted as an inline resolvable thread. A finding ranking below the floor in `SEVERITY_ORDER` (`["high","question","medium","low","nit"]`) folds into a collapsed `<details>` block in the verdict-marker body rather than posting inline (`GATE-COMMENT-INLINE-SEVERITY-FLOOR`, `skills/docs/gate-review-comment-contract.md`). At the default floor `high`/`question`/`medium` post inline unchanged and `low`/`nit` fold. Fold, not delete: each folded entry keeps its full visible `file:line` + summary text plus the same invisible fingerprint+`disposition=deferred` marker a body-filed finding carries, so cross-round fingerprint suppression still renders it exactly once. A folded finding creates no gate-authored thread, so it never enters `unresolvedGateThreadCount` and never blocks ready-for-review. Because folded findings never resolve a thread, the net-reduction filing moves onto them directly: `close-gate-findings.mjs`'s folded-filing pass files an operator-visible folded `low` to the PR's ONE tracked follow-up issue (deduped by fingerprint, sharing the thread pass's issue), while a `nit` or a non-operator-visible `low` files nothing — the folded block is its resolved-with-rationale record. `blockCleanOnFindingSeverities` is untouched: the verdict is computed upstream from the ledger, never from which surface a finding renders on, so a blocking-configured `low` still blocks a clean verdict even when folded. An unrecognized severity or floor fails OPEN (posts inline), never silently hidden. A `question` never folds at any floor — even a floor raised to `"high"`, where it would otherwise rank below `SEVERITY_ORDER`: a question is answered, not deferred, and its resolvable thread is what blocks gate-close until answered, so folding it would let an unanswered question slip past ready-for-review.

Rejected: deleting or dropping sub-floor findings (a mislabeled real defect would vanish — the fold keeps every finding fully visible and fingerprint-tracked); a global (non-per-gate) floor (the two gates already carry per-gate `blockCleanOnFindingSeverities`/`mediumFixWindow`, so the floor follows the same per-gate shape); and making the floor a hard drop with no escape hatch (lowering it, e.g. to `"low"` or `"nit"`, restores full inline posting, which is the cross-harness non-regression lever).

## Consequences

The default PR now surfaces only `high`/`medium` findings as inline threads; `low`/`nit` collapse into one folded section per round, folded further Outdated by [0073](./0073-fold-superseded-gate-verdict-reviews-as-outdated.md) as heads advance. Ready-for-review is no longer gated on disposing low-value threads that never should have been threads. Two costs are accepted. The folded-filing pass recomputes the sub-floor set from the round's ledger rather than from thread state, so it reads the follow-up issue's existing fingerprints for idempotency (one extra issue read only when an operator-visible folded `low` is present). And a repo wanting the old full-inline behavior must set `inlineSeverityFloor` low explicitly — the new default is suppression, not parity.
