# 0088. Reject-close an answered `question` thread the judge rejected

## Status

Accepted — 2026-09-23 ([issue 2381](https://github.com/mfittko/dev-loops/issues/2381))

## Context

A `question`-severity gate finding is answered, never deferred (`close-gate-findings.mjs`): an unanswered question blocks gate-close exactly like an open defect, forcing an operator or fixer to answer it before the thread can resolve. That works when the judge disposes the finding `act` (the fixer's own answer-and-resolve path replies and resolves it) or `defer` (judge-pass's relevance defer files it). It has no resolution path when the judge disposes the finding `reject`: a rejected finding never enters the fixer's act list (deliberately, so the fixer never spends a cycle on a finding the judge already ruled out of scope), so nothing ever posts the reply-and-resolve `close-gate-findings.mjs`'s own documented rule requires before it will treat the thread as closed. Once someone answers a judge-rejected question on the merits, the thread still counts as unresolved forever: `unresolvedGateThreadCount` never reaches 0, and `ready-for-review.mjs` refuses indefinitely with no remedy that can clear it — observed on PR #2365 and unblocked there only by a documented one-off manual resolution, which is a workaround, not a fix. The two lifecycle detectors compounded the same gap: `detect-pr-gate-coordination-state.mjs` never folded the gate-authored thread count into its own `mark_ready_for_review` decision at all, so it could report the PR ready while `detect-checkpoint-evidence.mjs`'s independent thread count still reported it blocked.

## Decision

`close-gate-findings.mjs` closes a gate-authored `question` thread when BOTH hold: the thread carries a resolving ANSWER REPLY, and the judge's own disposition for that finding is `reject`. A resolving answer reply is identified by WHAT IT IS, never by WHO POSTED IT: a non-empty, non-bot, non-System/ghost comment on the thread other than its own finding/marker comment, that is not itself the gate's own automation output (a posted finding/marker, or a disposition/reject-close/nit-rationale reply this file itself emits) and is not a bare `@copilot`/`/copilot*` summon. Author identity ("posted by someone other than the gate's login") is deliberately NOT the criterion: a single-account setup, where the gate, the fixer, and the operator all post as the same authenticated login, makes an identity check untrue for every reply and would leave the pass permanently unable to fire. An unanswered question carries no qualifying comment and keeps blocking, unchanged. The closing reply cites the judge's rejection rationale, resolved tiered current-round-ledger-first (the finding's own `judgeRationale`, cheapest, already in memory), then a PRIOR round's local findings-log ledger file for the same repo/pr/gate (the judge may have rejected the finding several rounds ago, and a re-raised finding is suppressed from the current ledger once already posted), then — last resort, rationale-less — the ` — judge: reject` suffix already rendered on the thread's own posted comment (`renderFindingLine`), which survives a fresh worktree/clone with no local ledger history. This never stamps `disposition=deferred` (it is not a deferral) and never files a follow-up issue (a question is never fileable, `isFileableDeferral`) — it is a NEW disposition kind, reply-and-resolve only, parallel to the existing unfiled nit/non-operator-visible-low resolution path. An answered question the judge did NOT reject is untouched, still owned by the fixer's own answer-and-resolve path; a `deferred` stamp on a locatable question remains a `GATE-EXEC-THREAD-DISPOSITION` contract violation, unchanged; a body-filed (non-locatable) question remains deferred by construction, unchanged (it never has a thread to reject-close).

`ready-for-review.mjs` refuses on exactly the set `close-gate-findings.mjs` reports unresolved (both read `countUnresolvedGateAuthoredThreads`/`fetchDraftGateEvidence`), and its refusal text now names a remedy specific to each reported blocking reason instead of one generic instruction that could not clear every case: an unanswered/not-yet-adjudicated `question` names "post a resolving answer reply, then rerun close-gate-findings"; an open defect thread (`high`/`medium`/`low`/`nit`) names the existing fixer fix-close / disposition-pass defer-close remedy. The severity breakdown (`countUnresolvedGateAuthoredThreadsBySeverity`) is a minimal additive extension of the shared surface, computed from the SAME thread fetch `countUnresolvedGateAuthoredThreads` already performs — no extra gh round-trip.

`detect-pr-gate-coordination-state.mjs` folds the gate-authored unresolved thread count into the core evaluator (`evaluatePrGateCoordination`'s `unresolvedGateThreadCount` input), which applies it ONLY to `draftGate.currentHeadClean` — the one predicate that gates `mark_ready_for_review` for a draft PR. When the round's `draft_gate` marker verdict is ALREADY clean but a gate-authored thread still dangles, the evaluator returns a distinct result (`reply_resolve_review_threads` / `feedback_resolution`) naming the thread blocker directly, ahead of the CI-status checks — neither `run_draft_gate` (re-running an already-clean gate round) nor a CI-blocked/`wait_for_ci` result (which would let CI pending/failing mask the real blocker) can ever clear a dangling thread, so neither is a legal answer here. The detector resolves the authenticated login (reusing the pattern `close-gate-findings.mjs`/`ready-for-review.mjs` already use) only when at least one candidate marker-bearing thread exists, narrowing the count to author identity — the exact same set those two scripts count — rather than the broader marker-only proxy; a login-resolution failure fails closed (-1), same as an unreadable thread payload. The detector reuses the SAME raw review-thread payload it already fetches for its own unrelated Copilot-loop bookkeeping (`countUnresolvedGateAuthoredThreadsFromRawNodes`), so the thread fetch itself costs no extra gh call — but the login resolution described above is its own extra `gh api user` call, made only when a candidate marker-bearing thread exists (a marker-only count of 0 skips it entirely). We rejected re-adding a detector-side post-pass (the shape [PR 2391](https://github.com/mfittko/dev-loops/pull/2391) deliberately removed by moving the equivalent draft-evidence rule into the core evaluator) in favor of the single core-evaluator decision point that rule already established. Folded in while reconciling the two detectors: `applyDraftGateEvidenceGuard` (the core evaluator's post-draft merge-path guard, `DRAFT_GATE_EVIDENCE_GUARDED_BOUNDARIES`) ran unconditionally on every return path, including a still-draft PR — rewriting an in-progress `COMPLETE_FIXER_DISPOSITION` (fixer-disposition boundary, `FEEDBACK_RESOLUTION`) to `reconcile_draft_gate` while draft_gate evidence is simply not yet posted for this round, the normal state mid-remediation. The guard now exempts `prDraft` PRs entirely (mirroring the wrapper's own pre-existing `prDraft` exemption for the title-marker guard), since it exists for the POST-draft merge-path boundaries only and the `PR_DRAFT` branch already owns in-draft state correctly.

Rejected: auto-resolving an unanswered question, or resolving any thread without a recorded judge disposition (non-goal — an unanswered question must keep blocking so an operator/fixer actually answers it); changing `question`'s severity semantics, `needs-answer` disposition, or `SEVERITY_ORDER` position; widening the ready-guard refusal's remedy text into a single reason bucket (the whole point is naming the remedy that can actually clear each reported reason); retrofitting the PR #2365 manual resolution (that PR is unblocked and out of scope).

## Consequences

An answered, judge-rejected `question` thread now has a sanctioned, automatic resolution path — the deadlock this record fixes can no longer recur, and the PR #2365-shaped manual workaround is no longer needed for any future occurrence. `ready-for-review.mjs`'s refusal is now actionable per reported reason rather than a single instruction that was sometimes provably unable to clear the count. `detect-pr-gate-coordination-state.mjs` and `detect-checkpoint-evidence.mjs` can no longer disagree about `mark_ready_for_review` for the same PR state. This is consistent with [ADR 0078](./0078-judge-adjudicates-every-finding-on-merits.md) (the judge's `reject` disposition becomes the recorded authority the reject-close reads back, on its own merits, not a severity shortcut) and [ADR 0075](./0075-fold-sub-floor-findings-out-of-inline-threads.md) (a `question` still never folds and still always posts an inline resolvable thread — this record only adds a resolution path for an already-posted thread, never changes which findings get one). The trade-off: the reject-close reply's rationale is only as good as what survived to the tiered lookup — the last-resort rendered-suffix tier carries the disposition but not the original rationale text, so a very old, cross-worktree reject-close cites a generic on-the-merits note instead of the judge's original words.

Known limitations, recorded rather than fixed here (both out of scope, [issue 2381](https://github.com/mfittko/dev-loops/issues/2381)): (1) the tier-3 rendered-suffix match (`parseRenderedJudgeDisposition`) is a byte-identical shape match, not a structural one — a reviewer/LLM-authored summary that happens to end with the exact same single-spaced ` — judge: <token>` shape is indistinguishable from the genuine suffix by string shape alone; closing that gap needs a render-time distinguishing token in `upsert-checkpoint-verdict.mjs`/`renderFindingLine`. (2) `detect-checkpoint-evidence.mjs`'s own unresolved-gate-authored-thread count (`countUnresolvedGateAuthoredThreadsFromRawNodes`) counts every MARKER-bearing thread, not only ones this reject-close pass can act on; it can diverge from `close-gate-findings.mjs`'s own count only on a foreign (non-gate-authored) thread that happens to quote a gate marker shape — a case the generic unresolved-thread count (not this ADR's reject-close logic) already blocks `mark_ready_for_review` on regardless, so the divergence never masks a real blocker.
