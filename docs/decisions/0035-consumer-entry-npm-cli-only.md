# 0035. Make the published npm CLI the only consumer entry point — a plugin marketplace checkout is distribution, never runtime

## Status

Accepted — 2026-07-18 ([PR 1384](https://github.com/mfittko/dev-loops/pull/1384))

## Context

The Claude Code plugin ships from `.claude/` via the marketplace catalog, and a `/plugin marketplace add` / `/plugin install` checkout carries prompts, skills, agents, and hooks — but Claude Code plugins run no install hook, so the checkout has no `node_modules`. In that state every local entrypoint importing `@dev-loops/core` fails with `Cannot find package '@dev-loops/core'`, including `dev-loops doctor` itself, which imported core at module top level and crashed before printing anything — the one tool meant to diagnose the condition was broken by it ([issue 1379](https://github.com/mfittko/dev-loops/issues/1379), observed live when an operator had to reverse-engineer the failure and fall back to a full repo checkout). The fix landed as [PR 1384](https://github.com/mfittko/dev-loops/pull/1384) (merged 2026-07-18): a zero-dependency `import.meta.resolve` probe in `cli/index.mjs` plus a `doctor` `core-resolvable` check, and the README's "Consumer entry contract" section now states the split explicitly. The single-source CLI subcommand reference that the contract paragraph points to is tracked separately in [issue 1376](https://github.com/mfittko/dev-loops/issues/1376).

## Decision

The plugin distribution carries no runtime: every command execution goes through the versioned npm CLI (`npx dev-loops@<version>`), and running raw `node scripts/*.mjs` against a plugin/marketplace checkout is unsupported, not merely discouraged. The CLI enforces this fail-closed with a zero-dependency preflight: `isCoreResolvable()` resolves `@dev-loops/core` without executing it, and when the probe fails, core-needing commands print one actionable stderr line pointing at the npm CLI and exit 1 before importing or spawning anything core-dependent, while `help`, `status`, and `doctor` stay pure-local so they keep working in the deps-less checkout and `doctor` names the condition. We rejected making the checkout self-sufficient (plugins cannot run install hooks, so bundling or installing dependencies there is not available), we rejected a try/catch dynamic import in favor of the resolve-only probe (the probe must run in the very broken state it diagnoses), and we rejected lazy-importing the top-level harness dependency — it was dead code and was deleted outright. The unpinned `npm install -g dev-loops` global remains a bare-shell convenience only; the pinned `npx` invocation is the contract path because it cannot drift from the plugin/extension version.

## Consequences

Distribution (plugin assets: prompts, skills, agents, hooks) and execution (the published npm CLI) are cleanly split, which shapes every harness surface: the Claude Code plugin and Pi extension stay thin integrations whose commands shell out to the versioned CLI rather than to checkout-local scripts, and the doctor/preflight layer exists precisely to police that seam. An operator who lands in the unsupported state now gets one actionable line instead of a raw `ERR_MODULE_NOT_FOUND` dead end, guarded by a contract test asserting no top-level core import sits on the reachable path. The cost is a network dependency: consumers must be able to `npx` the pinned CLI version, and keeping CLI, plugin, and extension on the same `<version>` is the consumer's responsibility, with the preflight catching only the missing-runtime case, not version skew.
