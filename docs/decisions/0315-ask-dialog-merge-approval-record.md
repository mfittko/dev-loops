# 0315. An ask-dialog answer counts as merge approval through a harness-written record

## Status

Accepted — 2026-11-21 ([issue 3438](https://github.com/mfittko/dev-loops/issues/3438))

## Context

A size-budget-escalated or stable-release merge needs a fresh per-merge approval: an APPROVED review or an `approve merge <sha> [patch-id <id>]` comment. Agents never write that line (`OPERATOR-OWNED-LINE`). The operator and the agents share one GitHub credential. A comment an agent posts after an ask answer therefore looks the same as a forged one. The operator had to type a `gh pr comment` command by hand, which breaks the rule that the only human step is answering a question.

## Decision

The harness records the operator's ask-dialog answer. An agent does not.

- Trust model. The operator's answer reaches the PostToolUse `AskUserQuestion` hook as tool output that the harness produces. No agent tool call writes it. A record written by that hook is human attestation. A comment an agent posts is not, because an agent holds the same credential and can post any text.
- Question. The orchestrator asks `Approve merge of <owner/name> PR #<n> at head <40-hex> with patch-id <40-hex>?` with the options exactly `Yes` and `No`, single select. The hook parses the facts from the question text and requires exactly one repo, PR, head and patch-id. Only the answer exactly `Yes` records an approval.
- Record. On a yes answer the hook writes `{repo, pr, headSha, patchId, question, answer, time, session}` to `~/.config/dev-loops/merge-approvals/<id>.json`. The directory is outside every checkout and every agent-writable path. `DEVLOOPS_APPROVAL_DIR` overrides it only when `DEVLOOPS_APPROVAL_TEST_MODE=1` is also set, so tests can isolate it and an agent-set variable cannot redirect the verifier.
- Integrity proof (the named mechanism). An HMAC-SHA256 over the canonical record, keyed by a random 32-byte key in `.key` (mode 0600) in the same directory (mode 0700). The hook creates the key exclusively (`wx`, then reads on `EEXIST`), requires exactly 32 bytes, and refuses a symlinked key or directory, a loose mode and a foreign owner. The record id is a second HMAC over the first, and the reader recomputes it and compares it to the file name. The record temp file is written with `wx`. The merge wrapper recomputes the HMAC and compares in constant time. An agent that cannot read the key cannot produce a valid record.
- Path guard. `pre-tool-use-approval-guard.mjs` denies Bash, Read, Edit, Write, NotebookEdit, Grep, Glob and MCP tool calls whose string arguments name the directory or the override variables. It compares paths case-folded and realpath-resolved and scans every argument for the directory name, which covers Glob patterns and Grep globs. File bodies are not scanned.
- Settings. The shipped `.claude/settings.json` adds `permissions.deny` entries for Read, Edit, Write and NotebookEdit on the directory and a `sandbox.filesystem.denyRead` entry. The permission denies are a second layer that does not depend on the hook parsing the call. The sandbox read deny is a further layer only when the sandbox is enabled; the shipped settings do not set `sandbox.enabled`, so by default it adds nothing. The guard also denies arguments naming the parent `.config/dev-loops`.
- Directory resolution. The directory comes from `os.userInfo().homedir`, not `$HOME`. The verifier ignores the `DEVLOOPS_APPROVAL_DIR` override when it runs with the real process environment. Only an injected env object (tests, and the hooks' own copy of their environment) with `DEVLOOPS_APPROVAL_TEST_MODE=1` redirects it.
- Patch-id. The patch-id is optional end to end. The merge check prints no patch-id when the head lacks the base tip. The question, record and posted line then carry the head only, and verification matches the head only.
- Key creation. The hook writes the key to a temp file and links it into place, so a partial key never appears at `.key`.
- Comment. The hook posts `approve merge <head> patch-id <id>` and a marker line `<!-- dev-loops:ask-approval id=<record-id> -->` through `gh`. GitHub keeps the visible audit trail. Agents cannot post the line (the raw comment write deny and `OPERATOR-OWNED-LINE`). The hook tells the model the outcome (recorded, post failed, or answer not recorded) through `additionalContext`.
- Reader (decision H1: require the record). Once this machine holds the hook key (the key file exists in the approval directory), `merge-pr.mjs` accepts an approve-merge comment only with a valid record for the same repo, PR, head and patch-id, where the head or patch-id equals the current one. This includes a comment the operator types by hand: it carries no marker and is refused. A marked body with more than one approve-merge line is refused. Only an absent key file (ENOENT) counts as no key; any other error reading it counts as present, so the verifier fails closed. Each refusal names its recovery (`RECOVERY-COMMAND-REQUIRED`): ask the approval question again with the current facts. A key or directory problem (wrong size, 0 bytes, loose mode, symlink, unwritable, unreadable) has a distinct refusal: the operator removes `<approval directory>/.key` or fixes its mode, then answers again, or the merge runs where the verifier can read the approval directory. The refusal also names a Pi-capable path: an APPROVED review on the current head, or running the merge under Claude Code. A Pi session on a machine that also holds the key is refused. This is an accepted consequence of H1. Without the key (Pi and other harnesses) the plain comment path is unchanged (#1086). On a machine with the key only the hook-posted line counts.
- Cross-reference. `MERGE-ASK-APPROVAL` is cited from `GATE-EXEC-OPERATOR-LINE-APPROVE-MERGE` and from the `merge_approval` refusal reason.

## Consequences

Under Claude Code the operator answers a question instead of typing a command. A machine that has used the hook no longer accepts a hand-typed line. The operator answers the question again, which is the same single human step.

Limits. The key protects against agent tool calls the hooks and settings judge. A same-user process that bypasses them (a wrapper script, a shell function, an unhooked harness or a Bash call that builds the path at run time) can read the key. The guard scans text, so shell indirection such as `cd` into the directory by parts, or shell globbing such as `~/.conf*/dev-*/merge-*`, defeats it. The guard also denies a bare mention of the directory name in a commit message or a `gh` body flag, because it cannot tell a mention from an address. An error inside the guard denies the call (exit 2). Deadlock risk: the sandbox read deny, when a user enables the sandbox, can make the verifier itself unable to read the key. The verifier then fails closed and refuses every approve-merge comment until the merge runs where it can read the approval directory (the refusal says so). The shipped settings leave the sandbox off, so the default setup does not hit this. This matches the ceiling of `OPERATOR-DECISION-RECORDER`. The hook does not check the live head at answer time. The merge wrapper checks currency at merge time. A machine without the key falls back to the comment path, so removing the key file disables the requirement, and the key lives in a directory the guard denies to agents.

Weakening `OPERATOR-OWNED-LINE` and changing which merges need fresh approval are out of scope.
