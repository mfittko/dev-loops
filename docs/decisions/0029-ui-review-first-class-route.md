# 0029. Make ui_review a first-class dev-loop route with a five-stage CLI pipeline and a per-project recipe contract

## Status

Accepted

## Context

Review loops verified code and text evidence only — the reviewer/fixer route reads the diff, tests, and gate comments, but nothing proved a change actually worked in the running app, and no route existed for browser-driven review with its own safety envelope ([issue 1114](https://github.com/mfittko/dev-loops/issues/1114)). The epic was grounded in a hand-run runbook against a real UI PR in a downstream repo: the live loop surfaced three defects the diff-only review missed (two user-facing HTTP 500s) and overturned a wrong static hypothesis, which is exactly the class of evidence the existing routes cannot produce. The route landed as staged slices — scaffold and route registration ([PR 1279](https://github.com/mfittko/dev-loops/pull/1279)), provision+boot ([PR 1280](https://github.com/mfittko/dev-loops/pull/1280)), the Playwright drive harness ([PR 1281](https://github.com/mfittko/dev-loops/pull/1281)), diagnose+anchor ([PR 1282](https://github.com/mfittko/dev-loops/pull/1282)), the pending-review report stage ([PR 1286](https://github.com/mfittko/dev-loops/pull/1286)), teardown with a side-effect ledger ([PR 1288](https://github.com/mfittko/dev-loops/pull/1288)), and the command help plus per-project recipe contract ([PR 1289](https://github.com/mfittko/dev-loops/pull/1289)) — and was activated as a runnable CLI route via subcommands and a `--ui-review` selector ([PR 1396](https://github.com/mfittko/dev-loops/pull/1396)). The stage behavior and envelope are documented in `skills/ui-review/SKILL.md`.

## Decision

We register `ui_review` as a first-class internal strategy with its own routing contract entries: a new `REVIEW_PR_UI` public intent and a `UI_REVIEW` gate that intercepts a PR target ahead of the ownership-derived PR gates (external/reviewer/Copilot) but after the authoritative lifecycle stop/terminal/approval/waiting gates, so an explicit UI-review request can never bypass them and the branch is inert without the signal. The route decomposes into five staged CLI subcommands — `ui-review-provision`, `ui-review-drive`, `ui-review-diagnose`, `ui-review-report`, `ui-review-teardown` — whose result JSON the orchestrating agent threads stage to stage; we rejected a separate chaining orchestrator as a component with nothing to own. A strict envelope bounds every stage: no product-code writes, worktree-only operation (provision refuses the primary checkout), an always-emitted side-effect ledger, and drive-session row tagging so teardown drops exactly the dev-DB rows the drive created — guessing at untagged rows was rejected in favor of failing closed with "rows may remain". Each drive step captures semantic evidence (screenshot plus `state.json`, `snapshot.json`, `axe.json`, `console.json`), the lens stage enforces per-acceptance-criterion `AC<n>` traceability with a computable coverage gate, and all project-specific knowledge — boot command, readiness probe, dev-login, flow allowlist, migration guards — lives in a per-project `uiReview` recipe in `.devloops`; hard-coding any project's boot or login into the route was rejected outright. Activation is deterministic: `dev-loops loop startup --pr <n> --ui-review` routes to the strategy, and the plain `--pr` path stays byte-identical.

## Consequences

A review sibling of reviewer/fixer now exists with its own state slugs, artifact model, and safety envelope, so "prove it in the running app" is a routed strategy rather than an ad-hoc manual runbook. Per-project recipes carry all app-specific knowledge, which means downstream repos onboard by declaring a recipe instead of forking the route, and future review modalities (visual diffing, cross-browser matrices, the GitHub-native artifact fallback) extend this contract rather than inventing new routes. The price is a real contract surface to maintain — five stage schemas, the envelope's stop rules, and the recipe shape — and known fail-closed gaps (the row-drop seam, non-Claude artifact hosting) that are tracked follow-ups rather than silent no-ops.
