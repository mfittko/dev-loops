dev-loops

A Deep Dive: Coordination Delay and the Waiting Between Actions

AI agents made writing code cheap. The cost moved to the coordination around it — author to reviewer, reviewer to CI, CI back to a human — where the hours leak while work waits to be handed over. dev-loops keeps the next step always known, so whoever is free pulls it from the visible state, and it turns the waiting between actions into something you can measure.

Part 1 · Eliminating coordination delay

The core idea

The Next Step Is Always Known

  • Like a Kanban board. The system computes the next action for any change; whoever is free pulls it from the visible state, so the handoff turns optional.
  • Who acts next? An outer loop reads that next action each cycle and makes one move at a time.
  • The PR's life. An inner loop walks each pull request from first draft to merged, one explicit step at a time.
  • The feedback. A second inner loop tracks every review comment from raised to resolved, so nothing gets lost.
  • When the next action is ambiguous, it stops and asks before acting.

Safe pauses

Pauses Only at Safe Boundaries

  • Pause now — it's safe to hand control to a human this instant.
  • Pause at the next clean boundary — finish the step in flight first, then stop.
  • Blocked — a required check is missing, so the work holds.
  • A pull request advances only after its review actually runs. The gate fails closed.

Example

You ask it to stop. If it's mid-edit, it doesn't drop the file — it tags the request stop_at_next_safe_gate and pauses the moment the current step lands clean. You get a tidy stopping point at a clean boundary.

Mid-flight steering

Change the Rules Mid-Run

  • A hard rule — a constraint the next steps must obey.
  • A preference — a nudge it tries to honor when it can.
  • A question — a clarification it folds into its next move.
  • Stop when safe — wind down at the next clean boundary.

Example

Halfway through, you say "don't touch the auth module." It lands as a hard_constraint the remaining steps must honor; the rule takes effect from the next move on, with progress preserved.

Parallel review

Many Reviewers, One Verdict

  • Every reviewer reads the same evidence bundle — the same diff, the same context — so their verdicts are directly comparable.
  • Each looks from a different angle (scope, test coverage, security) at the same time.
  • The findings merge into one verdict.
  • A single serious finding blocks the merge.

It never lies about being done

"Done" Means Merged

A human merges

  • Merging is reserved for a human.
  • At the final gate it hands the PR to a named person.
  • A human always owns the last yes.

"Done" is real

  • The board shows done only when a PR actually merged.
  • It reads the real merge signal from the source of truth.
  • Each task runs in its own isolated workspace.

Green is checked

  • CI-green is verified against the real result.
  • Works with any CI provider.
  • It waits for the real result before reporting.

Why a state graph

State Graphs Pin Behavior

  • Steer a workflow with prose alone and its behavior shifts with every model update, longer context, or change in temperature, with no warning.
  • dev-loops runs the workflow on a state graph: the moves are a closed, listable set, so the resolver computes the one next action for any change and surfaces it.
  • That is what makes the next step always known and pullable, and a known set of moves is testable, so a wrong transition is caught in CI.
Part 2 · Make the waiting visible

The delay pattern

One Interrupt, Five Transitions

  • A five-minute question costs the switch out, the rebuild, and the recovery on both sides.
  • Every interruption walks the same five steps — notice, switch, rebuild, act, recover — and each one has its own latency.
  • Across a queue of work, repeated interrupts multiply.

Handoff cost

Handoffs Restart Discovery

What the receiver pays for, every time

  • Reconstruct what changed since they last looked.
  • Gather enough context to act with confidence.
  • Confirm who owns it now and what's blocking it.
  • Absorb the round-trip if any of that is unclear.

Why it's worse with mixed actors

  • Ambiguous ownership pauses a human until they ask.
  • Missing context halts an AI agent — it guesses or stops.
  • Every human↔AI swap is one more place the state can drop.
  • More hands speed things up only when the state crosses intact.

The blind spot

Git History Hides the Wait

  • Commits record the output — leaving unrecorded the hours the work sat idle before someone touched it.
  • Review threads bury the cost of re-reading and re-explaining inside ordinary back-and-forth.
  • CI timestamps end at green. They miss the gap before a human notices and acts on the result.
  • So the single biggest drag on lead time — coordination waiting — is invisible to every tool you already trust.

Observable state

Four Fields Unblock the Next Actor

The fix is making the state of the work explicit, so picking it up becomes a continuation of work already in motion.

Keep these four current and the next actor — human or agent — starts immediately, with nothing to reconstruct.

State that turns pickup into continuation

  • Who owns it now — no guessing whose move it is.
  • What's blocking it — and what would unblock it.
  • The latest decision — so nobody re-litigates settled ground.
  • The safe next step — the one move that's known to be safe.

The measurement loop

Measure the Wait First

  • Capture the state, and the waits between actors become numbers you can point at.
  • Find the transition that stalls most, change the process there, and check whether the wait actually dropped.
  • Then confirm the change held quality steady, which is the step people skip.

From idea to instrument

The Fields Already Live in the Work

Owner & next step are a board

  • Work moves through visible columns: waiting, in progress, done.
  • The column is the current owner and the safe next step.
  • A deterministic resolver picks the next action and names whose move it is.

Decisions leave a trail

  • Each review gate records its verdict in the open, with the findings behind it.
  • The latest decision is written down for the next actor to read.
  • Pick the work up tomorrow and the reasoning is still there.

Automate only where it's safe

  • The wait at CI is handled by waiting on the real result, on any provider.
  • After a merge, finished workspaces are reclaimed and long-done items archived.
  • Automation runs only where the state says continuing is safe.

Why it pays off

Visible State Moves Three Numbers

Quality

  • Fewer wrong resumptions from stale context.
  • Cleaner fix loops.
  • Regressions are easier to trace back.

Waiting time

  • Faster first action after a handoff.
  • Context is already present at pickup.
  • Approvals stop sitting unnoticed.

Throughput

  • Higher flow efficiency.
  • Fewer items stalled in the dark.
  • Less coordination drag per merge.

The takeaway

Keep the Next Step Known, Measure Every Wait

  • Keep the next step always known, so whoever is free pulls it and a handoff, when it happens, is a recorded decision you can see.
  • Make the state explicit, and pickup becomes a continuation of work already under way.
  • Measure the waits, and the biggest stall stops hiding behind your commit history.
  • Automate only where state proves it's safe, and you remove the stall while keeping the judgment human.

Keep the next step known so the next actor pulls it, and measure how long the work waits.
