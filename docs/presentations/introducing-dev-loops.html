Introducing dev-loops

A coordination runtime for AI-assisted development. The next step is always known, so whoever is free pulls it from the visible state, and a person merges by default.

The problem

Coordination Is the Cost

  • AI writes the code in seconds, so the expensive part of the work moved.
  • It now sits in the coordination around the code: the wait for someone to notice a change is ready, to rebuild context to review it, to decide the next step is safe.
  • That waiting between actions is where the lead time of an AI-assisted workflow goes once the typing is fast.

Why it caps throughput

Manual Handoffs Compound

  • Every change carries a handful of transitions: is it ready, who reviews it, did review pass, is CI green, is it safe to merge.
  • Each one a person handles by hand is an interrupt with its own switching cost.
  • Their number is the transitions per change times the volume, so hand-run coordination acts like a power over the throughput.
  • A person's effective load grows far faster than the change count, and that caps how much an AI-assisted team can ship.

The idea

The Next Step Is Always Known

Pull, like a Kanban board

  • The system computes the next action; whoever is free pulls it from the visible state.
  • Every change still runs the same draft, review, and green-CI path, including the changes that built dev-loops itself.

A person merges by default

  • The loop prepares the change and reports it ready.
  • A human makes the final call, and you choose how much autonomy to grant.

Work starts from an artifact

  • A change begins from a short local plan or a tracked issue.
  • That artifact is the spec, carried through review to merge.

What it does to the work

One Decision per Change

  • Each transition becomes a decision the system takes and records.
  • Every change follows the same path, so there is no bespoke ceremony to design and no question about what happens next.
  • A person is pulled in where one is genuinely needed: the merge, and anything the loop flags as ambiguous.
  • What is left for the human is roughly one bounded decision per change.

What it means for the engine

Model-Agnostic by Construction

  • The next action is always computed and visible, and every change runs the same draft, review, and green-CI gate.
  • The loop fails closed when a step is ambiguous, and a person merges by default.
  • Those guardrails bound what any single step can get wrong, so a strong open-source model can drive most or all of the work.

What that buys you

  • Cheaper to run, and self-hostable on models you control.
  • Frees you from depending on a single vendor.
  • The gate holds the quality bar where you set it, whichever model fills each step.

Run end to end on top-tier open-source models: DeepSeek V4, Kimi K2.6, MiniMax M3, Qwen 3.6, GLM 5.2.

Set it up

Install and Run a Loop

Install

Claude Code, from inside the editor:

/plugin marketplace add mfittko/dev-loops /plugin install dev-loops@dev-loops

Pi:

pi install npm:dev-loops

Run a loop with a direct command (Claude Code; in Pi drop the colon: /dev-loops start …):

/dev-loops:start 112 /dev-loops:auto 112 /dev-loops:continue 112 /dev-loops:continue /dev-loops:start-spike "…"

Read state, never start work:

/dev-loops:info 112 /dev-loops:status

/dev-loops:dev-loop is the catch-all router for plain-language intent. You never pick internal modes.

Three choices shape the posture

  • Where work starts. strategy.default reads local-first for a plan in the repo, or github-first for a tracked issue.
  • Automated review. refinement.maxCopilotRounds sets the review rounds; set 0 to turn Copilot off.
  • Autonomy. autonomy.humanMergeOnly keeps the merge a human's call. Begin with the defaults and dial each setting toward what your team is comfortable with.
