The record: what the loop knows

Trace

    Where the loops are

    • Pre-PR review. A reviewer reads the change before the first push. Findings go back to the developer while the work is still local.
    • The gate round. Review lenses fan out over one head, fan-in checks that every lens reported, and the judge decides per finding: act, defer or reject. Only the act list reaches the fixer.
    • Fix and re-gate. Every fix is a new head. Evidence for the old head is stale, so the round runs again. A fix window bounds how often.
    • The outer loop. Startup re-reads GitHub and the local artifacts every time. A new unit starts only after the previous merge has its retro checkpoint.

    What the record holds

    The state lives outside any one chat: the issue and its AC / DoD matrix, the pull request and its head SHA, CI, the gate verdicts per head, and the gate artifacts under tmp/ in the worktree.

    Each guard reads that record. A verdict counts only for the head it names. A changed spec makes every clearance from the old spec stale, even when the code did not change.

    A session can end and a new one can resume. Startup reads the same record and computes the same next step.

    Who decides what

    Agents write code, review it and judge findings. Scripts decide whether a step may advance: coverage, validation, head identity, tripwires and merge preconditions. The operator decides intent, acceptance criteria, waivers and, by default, the merge.

    • Agents never write a waiver or an operator marker.
    • Scripts fail closed: an unknown result blocks, and a config load error never relaxes a gate.
    • The operator can grant a standing authorization to merge on a clean full gate.
