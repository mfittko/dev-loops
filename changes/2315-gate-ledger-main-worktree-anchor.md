### Fixed

- **Gate findings-log ledgers now land under the MAIN checkout's `tmp/`, not the ephemeral linked-worktree cwd — fixing recurring cross-worktree merge-provenance refusals and `executionMode: null` (issue [#2315](https://github.com/mfittko/dev-loops/issues/2315)).** `buildLogPath` resolved the ledger dir cwd-relative, so a coordinator running the gate inside `tmp/worktrees/<slug>/` wrote its ledger under that ephemeral worktree's `tmp/`. The orchestrator's merge (`merge-pr` / `detect-checkpoint-evidence`) runs from the MAIN checkout, so it could not read the worktree-local provenance and refused: "requireFanoutProvenance is enabled but the findings-log ledger lacks valid fan-out provenance" — despite valid provenance existing in the worktree ledger (observed on PRs #2304 / #2314). A new cwd-invariant `resolveMainWorktreeRoot` / `resolveGateArtifactTmpRoot` (in `scripts/loop/_repo-root-resolver.mjs`) anchors the ledger at the primary git worktree (`git worktree list`'s first entry). `writeGateFindingsLog` writes there, and the ledger READERS that would otherwise miss it — `resolve-angle-carry-forward` (prior-round ledger, a miss hard-fails carry-forward), `emit-fanout-dispatch`'s re-gate detection (a miss silently bypasses the carry-forward guard), and `write-gate-context`'s prior-head disposition memory — all resolve to the same location. `detect-checkpoint-evidence`'s multi-checkout scan already reaches the main worktree, so its per-checkout shadow-defense scan is unchanged. The ledger now also records the round's real `executionMode` (never `null` for a `fanout_fanin` verdict). One stable per-repo ledger location: reachable by the merge and surviving linked-worktree pruning. The gate-context / gate-reviews bundle stays worktree-local by design (reviewers are directed into the worktree), and the cross-machine / stateless reconciliation path (comment `executionMode` + `--skip-fanout-ledger-check`) is unchanged.
